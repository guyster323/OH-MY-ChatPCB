# Deterministic KiCad Analyzer Adapter Design

## Goal

Extend the read-only `project.inspect` workflow with deterministic facts extracted from the saved KiCad schematic and PCB, while keeping optional external analyzers isolated, pinned, and fail-closed.

## Context

Phase 1 established the artifact inventory, whole-project digest, evidence freshness contract, disposable ERC/DRC validation, and the `project.inspect` daemon/CLI surface. Phase 2 adds facts without changing KiCad files or turning generation metadata into an authority. The saved `.kicad_sch` and `.kicad_pcb` files remain the source of truth; `.chatpcb.json` continues to record intent and optional evidence only.

## Design Principles

1. Facts are reconstructed from bytes on disk and are deterministic for a fixed input.
2. Built-in facts are always available when the corresponding KiCad file exists; a missing file is a typed skip, not an inferred empty design.
3. Fact identifiers are stable across repeated inspection and do not use random UUIDs generated by the analyzer.
4. Every fact records its source artifact, extractor, and confidence.
5. External adapters are optional, explicitly configured, versioned, checksummed, time-bounded, and never downloaded automatically.
6. Namespaces are isolated: an adapter cannot replace or mutate built-in facts.
7. Inspection is read-only. `project-copy` adapters receive a symlink-free disposable copy; `json` adapters receive only serialized inventory/source content keyed by relative paths. Both run from disposable directories and are never given saved-project paths.
8. Parse failures are visible diagnostics with partial facts where safe; malformed input never becomes a fabricated clean result.

## Scope

### Built-in deterministic analyzer

The first built-in adapter parses the KiCad S-expression files using a small tokenizer/parser with string, number, list, and atom nodes. It does not invoke KiCad or normalize the files.

For `.kicad_sch`, it emits:

- `schematic.summary`: file format version and counts of placed symbols, labels, wires, junctions, and no-connect markers.
- `schematic.component`: one fact per placed `(symbol ...)`, including stable UUID, reference, value, library identifier, footprint, position, rotation, unit, and source path.
- `schematic.pin-net`: one fact for each explicit net label or symbol pin stub that can be associated without guessing. Unresolved pin connectivity is reported as a diagnostic rather than silently joined.
- `schematic.net`: normalized named-net facts derived from labels and explicit generated symbol stubs, including endpoint references when available.

For `.kicad_pcb`, it emits:

- `board.summary`: file format version, layer names, board outline bounding box, and counts of footprints, pads, segments, vias, zones, and graphic items.
- `board.footprint`: one fact per footprint with stable UUID when present, reference/value, library name, layer, position, rotation, and pad count.
- `board.pad`: one fact per pad with parent footprint reference, pad number, type, shape, layer(s), position, size, drill, net ID, and net name.
- `board.net`: one fact per declared net with numeric ID and name.
- `board.segment` and `board.via`: normalized copper geometry and layer/net information.
- `board.unrouted`: a conservative geometry-independent count of nets that have fewer than two copper endpoints or no connected pad/track evidence; KiCad DRC remains authoritative for true connectivity.

The analyzer also returns a typed diagnostic list for missing files, malformed S-expressions, unsupported constructs, and unresolved references. Diagnostics never change the `validation` ERC/DRC result.

### Optional external adapter

An adapter definition is accepted only through an explicit `options.analyzerAdapters` entry or a future pinned configuration file. The definition must include:

```js
{
  id: 'kicad-happy',
  namespace: 'external.kicad-happy',
  command: 'absolute-or-explicit-command',
  args: [],
  version: 'immutable-version',
  sha256: '64 lowercase hex characters',
  timeoutMs: 30000,
  input: 'project-copy' | 'json'
}
```

The runtime hashes the configured executable before launch, rejects path traversal and non-absolute executable paths unless the command is explicitly allowlisted, and compares the observed hash with the pinned value. A missing executable, checksum mismatch, timeout, non-zero exit, invalid JSON, or schema violation produces a typed adapter result and no external facts. The process runs with a disposable project copy when `input: 'project-copy'`; its stdout is parsed as JSON and stderr is redacted using the existing provider redaction rules.

External output must be an object with a declared `schemaVersion`, `facts` array, and optional `findings` array. Each emitted fact is normalized under the adapter namespace and receives `extractor: "external.kicad-happy@<version>"`, the source artifact list, and a confidence of `deterministic` only when the adapter declares that confidence; otherwise it is `heuristic`. Duplicate IDs are namespaced and rejected rather than merged.

## Inspection result contract

`inspectProject()` preserves all Phase 1 fields and adds:

```json
{
  "inspection": {
    "facts": [
      {
        "id": "builtin.schematic.component:U1",
        "category": "schematic.component",
        "value": {},
        "sourceArtifact": "demo.kicad_sch",
        "extractor": "builtin.kicad-schematic@1",
        "confidence": "deterministic"
      }
    ],
    "analyzers": [
      {
        "id": "builtin.kicad",
        "namespace": "builtin",
        "status": "complete",
        "version": "1",
        "sourceArtifacts": ["demo.kicad_sch", "demo.kicad_pcb"],
        "diagnostics": []
      }
    ]
  },
  "findings": []
}
```

`inspection.facts` is sorted by `id`, then `category`, then a canonical JSON representation of `value`. `inspection.analyzers` is sorted by adapter ID. A fact ID is unique across all namespaces; a collision is a typed analyzer error and the colliding fact is omitted. Built-in facts are emitted even when an optional adapter is skipped.

Findings use the existing evidence vocabulary and may reference facts by ID:

```json
{
  "id": "builtin.board.missing-footprint",
  "severity": "warning",
  "confidence": "deterministic",
  "factIds": ["builtin.schematic.component:U1"],
  "sourceArtifacts": ["demo.kicad_sch"],
  "message": "..."
}
```

The initial built-in analyzer creates only structural findings (for example, a schematic component with no footprint or a PCB pad referencing an unknown net). It does not claim electrical correctness, manufacturing readiness, or datasheet compliance.

## Data flow and isolation

1. `inspectProject` validates the project path and computes the Phase 1 artifact inventory.
2. It reads the saved source bytes once and passes immutable buffers to the built-in analyzer.
3. It runs ERC/DRC in the existing disposable validation copy.
4. It runs configured external adapters against a separate disposable copy or JSON payload. JSON mode contains no original absolute project path, and both modes use a disposable child working directory.
5. It normalizes, namespaces, sorts, and returns facts, analyzer statuses, and fact-linked findings.
6. No analyzer writes the source project, manifest, reports, or evidence cache.

If a source file changes during inspection, the analyzer result is discarded and inspection returns `ANALYZER_INPUT_CHANGED`; the caller can retry against the new digest. This protects fact/artifact binding without introducing a write lock.

## CLI, daemon, and panel compatibility

The existing `chatpcb inspect --project <dir>` and `project.inspect` calls remain valid. Their JSON output gains `inspection.facts`, `inspection.analyzers`, and `findings`; existing consumers that read artifact and validation fields continue to work. The panel may render counts and diagnostics in a later UI task; Phase 2 does not make release decisions from facts alone.

## Error model

- `ANALYZER_INPUT_CHANGED`: tracked source bytes changed during analysis.
- `ANALYZER_PARSE_ERROR`: a KiCad source is malformed; safe facts from other files may remain.
- `ANALYZER_ADAPTER_UNAVAILABLE`: configured adapter executable is absent.
- `ANALYZER_ADAPTER_CHECKSUM_MISMATCH`: executable hash differs from the pinned hash.
- `ANALYZER_ADAPTER_TIMEOUT`: adapter exceeded its timeout.
- `ANALYZER_ADAPTER_INVALID_OUTPUT`: adapter stdout is not valid or does not match its schema.
- `ANALYZER_FACT_COLLISION`: two adapters emitted the same fully-qualified fact ID.

Typed diagnostics are returned in the analyzer status and do not masquerade as clean validation. External adapter failures do not prevent built-in facts from being returned.

## Testing strategy

- Fixture-based parser tests cover generated KiCad 10 syntax, nested paths, quoted/escaped strings, mixed layers, rotated footprints, pads with and without nets, and deterministic ordering.
- Repeated inspection tests compare complete fact and analyzer JSON byte-for-byte.
- Mutation tests change one source byte and assert a changed digest plus discarded/stale analyzer output.
- Read-only tests snapshot the project directory before and after built-in and external analysis.
- Adapter tests cover absence, checksum mismatch, timeout, malformed JSON, namespacing, duplicate IDs, redacted stderr, and disposable-copy writes.
- Integration tests assert CLI and daemon inspection expose facts while preserving Phase 1 validation and manifest freshness behavior.

## Non-goals

- Replacing KiCad's parser or making KiCad the analyzer's runtime dependency.
- Claiming complete electrical connectivity from text heuristics.
- Implementing placement/routing, Circuit JSON conversion, IPC mutations, or release promotion.
- Installing kicad-happy or any other external binary automatically.

## Success criteria

1. Fixed KiCad bytes produce identical facts, analyzer statuses, and finding IDs across repeated inspections.
2. Built-in facts remain available when external adapters are absent.
3. A missing, unpinned, corrupt, or checksum-mismatched adapter is never executed.
4. Analyzer processes cannot modify the saved project and any created files are removed with the disposable copy.
5. Every fact and finding is traceable to artifact paths and a versioned extractor.
6. Existing Phase 1 tests and CLI/daemon compatibility remain green.
